## 1. Общие сведения

### 1.1. Назначение документа
Настоящее техническое задание определяет требования к разработке сервиса мониторинга здоровья сервисов и отображения временной шкалы их состояний для экосистемы X-Lab.

### 1.2. Цель проекта
Создание централизованного сервиса для:
- Мониторинга текущего состояния здоровья всех сервисов в экосистеме
- Отображения исторической информации о состояниях сервисов на временной шкале
- Предоставления API для интеграции с другими сервисами
- Визуализации метрик и статистики доступности сервисов
- Предоставления публичного доступа к общей информации о здоровье системы
- Обеспечения приватного доступа к детальной информации для авторизованных пользователей

### 1.3. Область применения
Сервис предназначен для использования:
- DevOps-инженерами для мониторинга инфраструктуры
- Разработчиками для отслеживания состояния зависимых сервисов
- Менеджментом для получения общей картины доступности системы

## 2. Требования к функциональности

### 2.1. Мониторинг здоровья сервисов

#### 2.1.1. Сбор информации о состоянии сервисов
- **Описание**: Сервис должен периодически проверять состояние всех зарегистрированных сервисов
- **Требования**:
  - Поддержка различных типов проверок (HTTP endpoints, TCP соединения, проверка БД)
  - Настраиваемый интервал проверки для каждого сервиса
  - Поддержка таймаутов и retry-логики
  - Сбор дополнительных метрик (время отклика, использование ресурсов)

#### 2.1.2. Классификация состояний
- **Healthy** (Здоров) - сервис работает корректно
- **Degraded** (Деградирован) - сервис работает, но с ограниченной функциональностью
- **Unhealthy** (Не здоров) - сервис не работает или недоступен
- **Unknown** (Неизвестно) - состояние не может быть определено

#### 2.1.3. Хранение истории состояний
- Сохранение всех изменений состояний с временными метками
- Хранение метрик производительности
- Настраиваемый период хранения данных

### 2.2. Временная шкала состояний

#### 2.2.1. Отображение истории
- Визуализация изменений состояний сервисов на временной шкале
- Фильтрация по:
  - Периоду времени
  - Конкретному сервису или группе сервисов
  - Типу состояния
- Масштабирование временной шкалы (час, день, неделя, месяц)

#### 2.2.2. Аналитика
- Расчет метрик доступности (uptime/downtime)
- Статистика по типам состояний
- Выявление паттернов и трендов
- Экспорт отчетов

### 2.3. Режимы доступа

#### 2.3.1. Public (Публичный доступ)
- **Назначение**: Отображение общей информации о здоровье системы без авторизации
- **Доступная информация**:
  - Общий статус системы (Healthy/Degraded/Unhealthy)
  - Список сервисов с их текущими состояниями (без деталей)
    - Отображаются только сервисы с флагом `IsPublic = true`
    - Показывается только название, текущее состояние и время последней проверки
  - Общие метрики (количество публичных сервисов, количество проблемных)
  - Время последнего обновления
  - Общий процент доступности системы
- **Ограничения**:
  - Нет доступа к детальной информации о сервисах
  - Нет доступа к истории состояний
  - Нет доступа к метрикам производительности
  - Нет доступа к конфигурации и администрированию
  - Нет доступа к приватным сервисам (IsPublic = false)
- **Использование**: 
  - Публичные дашборды для отображения статуса клиентам
  - Встраивание виджета статуса на внешние сайты
  - API для интеграции с внешними системами

#### 2.3.2. Private (Приватный доступ)
- **Назначение**: Полный доступ к детальной информации для авторизованных пользователей
- **Доступная информация**:
  - Детальная информация о каждом сервисе (включая приватные)
  - Полная история состояний и временная шкала
  - Метрики производительности и аналитика
  - Конфигурация проверок
  - Управление сервисами и настройками (для роли Admin)
  - Логи ошибок и исключений
  - Настройка публичности сервисов (IsPublic флаг)
- **Требования**:
  - Обязательная аутентификация (JWT токены)
  - Авторизация по ролям:
    - **Admin**: полный доступ, включая управление
    - **Viewer**: доступ к просмотру всех данных без возможности изменений
- **Использование**:
  - Внутренний мониторинг для DevOps команды
  - Детальный анализ проблем и инцидентов
  - Управление конфигурацией мониторинга

### 2.4. API для интеграции

#### 2.4.1. Public REST API (без авторизации)
- **GET /api/public/status** - общий статус системы
- **GET /api/public/services** - список сервисов с базовой информацией (только состояние)
- **GET /api/public/services/{id}** - базовая информация о сервисе (только состояние)
- **GET /api/public/summary** - общая сводка (количество сервисов, статистика состояний)

#### 2.4.2. Private REST API (требуется авторизация)
- **GET /api/services** - полный список всех сервисов с деталями
- **GET /api/services/{id}** - детальная информация о конкретном сервисе
- **GET /api/services/{id}/status** - текущее состояние сервиса с метриками
- **GET /api/services/{id}/history** - полная история состояний
- **GET /api/services/{id}/metrics** - метрики производительности
- **POST /api/services** - регистрация нового сервиса (требуется роль Admin)
- **PUT /api/services/{id}** - обновление конфигурации сервиса (требуется роль Admin)
- **DELETE /api/services/{id}** - удаление сервиса из мониторинга (требуется роль Admin)
- **GET /api/health** - проверка здоровья самого сервиса мониторинга
- **GET /api/analytics** - аналитика и статистика (требуется роль Admin или Viewer)

#### 2.4.3. Аутентификация
- **POST /api/auth/login** - вход в систему (получение JWT токена)
- **POST /api/auth/refresh** - обновление токена
- **POST /api/auth/logout** - выход из системы

#### 2.4.4. Webhooks
- Отправка уведомлений при изменении состояния сервиса
- Настраиваемые события (переход в Unhealthy, восстановление и т.д.)
- Настройка webhooks доступна только для авторизованных пользователей с ролью Admin

### 2.5. Пользовательский интерфейс

#### 2.5.1. Public Dashboard (Публичный режим)
- **Доступ**: Без авторизации, открытый доступ
- **Функциональность**:
  - Общий обзор состояния всех сервисов
  - Индикаторы состояния (цветовая индикация: зеленый/желтый/красный)
  - Счетчики метрик (общее количество сервисов, количество проблемных)
  - Общий статус системы
  - Время последнего обновления
  - Минималистичный дизайн, оптимизированный для быстрой загрузки
- **Ограничения**:
  - Нет детальной информации о сервисах
  - Нет истории состояний
  - Нет метрик производительности
  - Нет возможности управления

#### 2.5.2. Private Dashboard (Приватный режим)
- **Доступ**: Требуется авторизация
- **Функциональность**:
  - Полный обзор состояния всех сервисов с деталями
  - Индикаторы состояния с дополнительной информацией
  - Расширенные счетчики метрик
  - Последние события и уведомления
  - Фильтрация и поиск сервисов
  - Группировка по тегам или типам

#### 2.5.3. Детальная информация о сервисе (Private)
- Текущее состояние и метрики производительности
- Временная шкала состояний с возможностью масштабирования
- История инцидентов с деталями
- Конфигурация проверок
- Графики метрик (время отклика, доступность)
- Логи ошибок (для роли Admin)

#### 2.5.4. Администрирование (Private, роль Admin)
- Управление списком мониторируемых сервисов
- Настройка параметров проверок
- Управление уведомлениями и webhooks
- Настройка периодов хранения данных
- Управление пользователями и ролями
- Настройка системы

#### 2.5.5. Аутентификация в UI
- Страница входа (Login)
- Управление сессией (автоматическое обновление токенов)
- Защищенные маршруты (Private Routes)
- Отображение информации о текущем пользователе

## 3. Технические требования

### 3.1. Стек технологий

#### 3.1.1. Backend
- **Платформа**: ASP.NET Core 8.0+
- **Язык**: C# 12
- **Архитектура**: RESTful API, возможно добавление GraphQL в будущем
- **Health Checks**: ASP.NET Core Health Checks
- **Real-time**: ASP.NET Core SignalR (для live обновлений UI)
- **ORM**: Entity Framework Core
- **Валидация**: FluentValidation
- **Логирование**: Serilog
- **Конфигурация**: IOptions pattern, appsettings.json

#### 3.1.2. База данных
- **Основная БД**: Microsoft SQL Server 2019+
- **Схема данных**:
  - Таблицы для хранения информации о сервисах
  - Таблицы для истории состояний (partitioned tables для оптимизации)
  - Таблицы для метрик
  - Таблицы для конфигурации проверок
- **Миграции**: Entity Framework Core Migrations
- **Резервное копирование**: Настраиваемые политики бэкапов

#### 3.1.3. Frontend
- **Платформа**: React 18+ с TypeScript
- **Сборщик**: Vite или Create React App
- **UI Framework**: Material-UI (MUI), Ant Design или Tailwind CSS
- **State Management**: Redux Toolkit или Zustand
- **Маршрутизация**: React Router
- **HTTP клиент**: Axios или Fetch API
- **Графики**: Recharts, Chart.js или Victory
- **Real-time**: @microsoft/signalr (SignalR Client для React)
- **Формы**: React Hook Form
- **Валидация**: Zod или Yup

#### 3.1.4. Дополнительные компоненты
- **Кэширование**: Redis (опционально, для повышения производительности)
- **Очереди задач**: Hangfire или Quartz.NET (для фоновых проверок)
- **Контейнеризация**: Docker
- **Оркестрация**: Docker Compose (для локальной разработки)

### 3.2. Архитектура разделения Public/Private

#### 3.2.1. Backend архитектура
- **Разделение контроллеров**:
  - `PublicController` - публичные endpoints без авторизации
  - `ServicesController` - приватные endpoints с авторизацией
  - `AuthController` - управление аутентификацией
- **Middleware для авторизации**:
  - JWT Bearer Authentication для приватных endpoints
  - CORS политики для разделения доступа
  - Rate limiting для публичных endpoints (защита от злоупотреблений)
- **Фильтрация данных**:
  - Публичные endpoints возвращают только базовую информацию
  - Приватные endpoints возвращают полную информацию
  - Использование DTO (Data Transfer Objects) для разделения моделей

#### 3.2.2. Frontend архитектура
- **Маршрутизация**:
  - `/` - публичный dashboard (без авторизации)
  - `/login` - страница входа
  - `/dashboard` - приватный dashboard (требует авторизации)
  - `/services/:id` - детальная информация о сервисе (требует авторизации)
  - `/admin` - администрирование (требует роль Admin)
- **Защита маршрутов**:
  - `PrivateRoute` компонент для защиты приватных маршрутов
  - Проверка токена и ролей перед доступом
  - Редирект на `/login` при отсутствии авторизации
- **Управление состоянием**:
  - Хранение токена в localStorage или httpOnly cookies
  - Context API или Redux для управления состоянием аутентификации
  - Автоматическое обновление токенов через refresh token

### 3.3. Интеграция с существующими сервисами

#### 3.3.1. Интеграция с ASP.NET API сервисами
- Использование стандартных ASP.NET Core Health Checks endpoints
- Поддержка кастомных health check провайдеров
- Аутентификация при необходимости (JWT, API Keys)

#### 3.3.2. Интеграция с MS SQL Server
- Мониторинг доступности БД
- Проверка производительности запросов
- Мониторинг размера БД и использования ресурсов

#### 3.3.3. Поддержка других типов сервисов
- HTTP/HTTPS endpoints (любые REST API)
- TCP соединения
- Проверка доступности баз данных
- Проверка файловых систем
- Кастомные проверки через плагины

### 3.4. Производительность

#### 3.4.1. Требования к производительности
- Время отклика API: < 200ms для стандартных запросов
- Поддержка одновременной проверки до 100 сервисов
- Минимальный интервал проверки: 30 секунд
- Хранение истории: минимум 90 дней

#### 3.4.2. Масштабируемость
- Возможность горизонтального масштабирования
- Поддержка нескольких инстансов сервиса
- Распределенная проверка сервисов между инстансами

### 3.5. Безопасность

#### 3.5.1. Аутентификация и авторизация
- **JWT токены** для аутентификации
- **Роли пользователей**:
  - **Admin** - полный доступ ко всем функциям, включая управление
  - **Viewer** - доступ к просмотру детальной информации, без возможности изменений
  - **Public** - неавторизованный доступ только к публичной информации
- **API Keys** для интеграций (опционально)
- **Refresh Tokens** для безопасного обновления сессий
- **CORS** настройки для разделения публичных и приватных endpoints

#### 3.5.2. Защита данных
- Шифрование чувствительных данных (credentials для проверок)
- HTTPS для всех соединений
- Валидация входных данных
- Защита от SQL injection, XSS

### 3.6. Надежность

#### 3.6.1. Отказоустойчивость
- Graceful degradation при недоступности БД
- Retry логика для проверок сервисов
- Circuit breaker pattern для проблемных сервисов
- Логирование всех ошибок

#### 3.6.2. Мониторинг самого сервиса
- Health check endpoint для самого сервиса мониторинга
- Метрики производительности (Prometheus format, опционально)
- Structured logging

## 4. Структура данных

### 4.1. Основные сущности

#### 4.1.1. Service (Сервис)
```csharp
- Id: Guid
- Name: string
- Description: string
- Url: string (endpoint для проверки)
- Type: ServiceType (HTTP, TCP, Database, Custom)
- CheckInterval: int (секунды)
- Timeout: int (миллисекунды)
- RetryCount: int
- IsEnabled: bool
- IsPublic: bool (отображается ли в публичном API)
- Tags: string[] (для группировки)
- CreatedAt: DateTime
- UpdatedAt: DateTime
```

#### 4.1.2. HealthCheckResult (Результат проверки)
```csharp
- Id: Guid
- ServiceId: Guid
- Status: HealthStatus (Healthy, Degraded, Unhealthy, Unknown)
- ResponseTime: int (миллисекунды)
- Message: string
- Exception: string (если есть)
- CheckedAt: DateTime
- Metadata: Dictionary<string, object> (дополнительные данные)
```

#### 4.1.3. ServiceConfiguration (Конфигурация проверки)
```csharp
- Id: Guid
- ServiceId: Guid
- CheckType: string
- Parameters: string (JSON)
- Headers: Dictionary<string, string> (для HTTP)
- ExpectedStatusCode: int (для HTTP)
- ExpectedResponse: string (опционально)
```

### 4.2. Схема базы данных

#### 4.2.1. Таблицы
- **Services** - информация о сервисах (с флагом IsPublic)
- **HealthCheckResults** - результаты проверок (partitioned по дате)
- **ServiceConfigurations** - конфигурации проверок
- **ServiceTags** - теги для сервисов
- **Incidents** - инциденты (периоды недоступности)
- **Metrics** - метрики производительности
- **Users** - пользователи системы
- **UserRoles** - роли пользователей (Admin, Viewer)
- **RefreshTokens** - токены для обновления сессий
- **Notifications** - настройки уведомлений

## 8. Критерии приемки

### 8.2. Нефункциональные требования

## 9. Риски и ограничения

### 9.1. Технические риски
- Перегрузка БД при большом количестве сервисов
- **Митигация**: Партиционирование таблиц, архивирование старых данных

- Задержки при проверке медленных сервисов
- **Митигация**: Асинхронные проверки, таймауты

### 9.2. Ограничения
- Зависимость от доступности мониторируемых сервисов
- Необходимость настройки каждого сервиса вручную
- Ограничения по хранению данных (зависит от ресурсов БД)
